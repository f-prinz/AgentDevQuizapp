# Codex-Auftrag: Iterative lokale Entwicklung

Du bist der Haupt-Orchestrator. Lies AGENTS.md, docs/orchestrator-checklist.md, docs/project-idea.md und docs/tech-stack.md. Nutze die bereits registrierten Subagents. Kein Deployment; Push nur Task-Branches bei Remote (`push-task.mjs`).

1. Führe `node scripts/sync-main.mjs` aus (main auf Remote-Stand, falls Remote). Prüfe, ob die Projektidee ausreichend konkret ist. Jede Anfrage beginnt mit der Klärungsphase (analyst stellt Rueckfragen oder begruendet 'kein Klaerungsbedarf'). Bei kritischen offenen Produktentscheidungen halte an und frage. Prüfe ausserdem offene Einträge in docs/changes.md und steuere sie gemaess den Playbooks ein (BUG/CHANGE/FEATURE).
2. Erstelle Requirements, Architektur und Tasks in tasks/state.json mit stabilen IDs (TECH/BUG/CHG/FEAT), Abhängigkeiten, Akzeptanzkriterien, Testbefehlen und inventory_refs — backlog.md wird generiert (`node scripts/render-backlog.mjs`), nie von Hand editieren. Klassifiziere relevante Aufgaben als CURRENT_STACK_ONLY, TARGET_ALIGNED oder REQUIRES_MIGRATION. Neue Komponenten nur via `node scripts/add-component.mjs`; danach `node scripts/verify.mjs`.
3. Wähle immer nur Tasks, deren Abhängigkeiten DONE sind. Setze Status via `node scripts/update-task.mjs <id> IN_PROGRESS --by <agent>` — Transitionen werden erzwungen (TODO→IN_PROGRESS→DONE/BLOCKED). Lege den Task-Branch via `node scripts/branch-task.mjs <id>` an; alle Task-Commits laufen dort (Name = Task-ID, Buchhaltung bleibt auf main). Bei `red_evidence_required` liefert der Test Engineer zuerst den roten Test, dann implementiert der Developer. Implementiere durch passende Subagents; der Task-Scope wird mechanisch geprueft.
4. Prueflaeufe als Evidence: `node scripts/record-check.mjs <TASK-ID> -- <befehl>` (rot = Exit != 0, gruen/lint = Exit 0). Nach Review: `node scripts/push-task.mjs <id>` (nur bei Remote), `node scripts/merge-task.mjs <id>` (Konfliktprognose inklusive). DONE nur auf main nach dem Merge via `update-task <id> DONE --test-evidence <file> [--red-evidence f] [--lint-evidence f] --reviewed-by <code_reviewer|security_reviewer> --review-result "<summary>"` — erfordert Reviewer != Implementer, erfuellte AK und bei FEAT/CHG/BUG mindestens einen INV-Eintrag (Verlinkung via `--add-inv`).
5. Bei Fehlern: maximal 3 gezielte Fix-Retries je Task (`node scripts/record-fix.mjs`); dann BLOCKED mit `--reason` und Diagnose. Keine Endlosschleife.
6. Nach jedem Task: state.json/backlog.md/progress.md aktualisiert update-task automatisch. Prüfe `node scripts/check-state.mjs` und `node scripts/check-inventory.mjs`.
7. Zum Schluss: vollständige lokale Validierung, Inventar-Audit gemaess docs/playbooks/audit.md (scope_auditor), erledigte Tasks via `node scripts/archive-tasks.mjs` archivieren, docs/final-report.md und lokale Startanleitung. Kennzeichne nicht ausgeführte Tests.

Arbeite nur im Projektordner. Respektiere Sandbox und Freigaben. Bei Sitzungsende oder Kontextlimit sichere zuerst den Zustand und gib einen präzisen Fortsetzungshinweis.
